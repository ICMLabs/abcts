`PW=… ENGINE=chrome node scripts/zzlive.mjs`

Nothing had ever run it. The arc opened on WebKit for a good reason, and then `d4b7022`'s
measurement — abcjs does not render byte-identically in WebKit and Blink, 230 of 691 — was

**The second does not follow.** abcjs disagreeing with ITSELF across browsers says nothing
about whether WE agree with IT in each. The cache port took Chrome 5 → 4 on the same change

✅ **THREE OF THE FOUR CLOSED ON 2026-09-04b**, and every one is something WebKit is
structurally unable to express:

- **`wrap-03` — A `%%<type>font`'s DEFAULT WEIGHT AND STYLE ARE PART OF WHAT IT MEASURES
  WITH** (`dd5bee8`). `initializeFonts` gives four types an ITALIC default and three a BOLD
  one; `fontOfType` read only what the SCORE had set, so all seven measured
  `normal`/`normal`. Blink inks an italic `6` at 9.982422 against an upright 9.5 at 19px —
  WebKit inks every digit at 9.5 either way. `tests/font-defaults.test.ts` is the
  instrument: it records the fonts the layout ASKS about, so it needs no browser and no
  golden. ⚠️ **`zzcontrol dirs` could not have caught this and never will** — every rung of
  it SETS a directive, so the default path never runs.
- **`wrap-04` — THE STAFF CONNECTOR'S FAR EDGE IS BUILT FROM THE ROUNDED ANCHOR**
  (`bb0c23a`). `printStem`'s `x = roundNumber(x); var x2 = roundNumber(x + dx)`, which
  `drawStaffGroup` uses for the left-edge rule (`staff-group.js:143`). ⚠️ **The rule was
  already ported TWICE** — `lineToRect`'s stem/bar branch and the beam's second edge — and
  this was a third copy nobody went back to. **A rule ported at the site that named it is
  not a rule ported.**
- **`text-udef-parts-overlays-tune23`** closed with them.

### ✅ THE LAST ONE — `options-01-fonts`, and it was an ASSOCIATION

A `P:` label's baseline: **ours 382.82, abcjs 382.81.** Not a measurement — a grouping.
`renderText` builds the baseline as three adds onto the PAGE's y and rounds ONCE
(`draw/text.js:29`, `:30-31`, `:58`, `:64`):

    ours    (t.y + pad) * PX + oy       382.81500000000005 -> "382.82"
    abcjs   ((rung + oy) + size) + pad  382.815            -> "382.81"

Same value by algebra, different double. **AN ASSOCIATION IS A DECISION.**

⭐ **AND THE ARITHMETIC WAS FOUR LINES WHERE THE WORK WAS THE FIVE FLAGS BEFORE IT.**
Recovering the rung means subtracting the font size back off `t.y`, which is right only for
a row that HAD one added — `renderText`'s centred branch takes no `+= font.size`, so a
centred row's `t.y` IS the rung. abcjs passes `centerVertically` at FIVE sites and we
modelled ONE:

    draw/voice.js:19      voice name          ← flagged, but ONLY INSIDE THE BOX OBJECT
    draw/relative.js:49   text decoration     ← added
    draw/relative.js:52   pitched annotation  ← added, at both sites
    draw/triplet.js:12    tuplet number       ← added
    draw/brace.js:92      brace's voice name  ← a separate emitter, never a PlacedText

The voice name is the one that mattered and it was already "done": `centered: true` sat
inside `nameBox`, gated on `voicefont.box === true`, so **every UNBOXED voice name was
missing it** — invisible while only the box branch read the flag, and exactly why a first
attempt at the regrouping took `zocharti-loch`, its `-classes` twin and `wrap-04`'s
`Violin II` red.

⭐ **A FLAG SET ON THE PATH THAT NEEDED IT IS NOT A FLAG SET** — the same shape as
`printStem`'s rounding, ported twice and missed a third time one commit earlier.

**The method that made it safe**: land the flags FIRST and measure them to be INERT (suite
and `svg-bytes` unmoved, because nothing read `centered` outside the box branch yet), then
regroup and re-run. `svg-bytes` is the arbiter for which sites are centred rather than any
reasoning about them — it is byte-exact against abcjs on 1,041 rows and goes red on a
single wrong flag.

⚠️ **DO NOT CARRY THE WEBKIT PLAYBOOK STRAIGHT OVER.** WebKit is at ZERO, so every one of
these is something only Blink's metrics express. A rounding boundary is the shape to expect,
and a rounding boundary is not fixed by measuring harder — it is fixed by matching abcjs's
ARITHMETIC, which is a different search from matching its FONT.

### 2 · THE MODES — ✅ **CLOSED 2026-09-04, BY A DECISION**

Everything this section listed is done, and the last item was the owner's call rather than a
measurement.

⚖️ **THERE ARE TWO MODES NOW: `abcjs-strict` AND `abcjs-extended`** (Lance, 2026-09-04).
`abc2.1` is REMOVED — not deprecated, gone from the type — and `extended` is renamed to say
what it is. The finding that forced it was a grep: **every mode branch in `src/` is
`isStrict(mode)`**, one comparison in `core/model.ts`, so `abc2.1` and `extended` were
byte-identical on all 691 corpus cases and both intended tiers had landed in one bucket —
the `+:`/`[U:`/`I:` parsing fixes beside the styled noteheads, tremolos, three-quarter-tone
glyphs and per-segment lyric fonts. A host asking for `abc2.1` got the beyond-standard
engraving too; one asking for `extended` got nothing extra.

**The type now carries what a corpus assertion used to.** "The modes have not collapsed into
one" is a compile error rather than a test, which is why two `it`s were deleted rather than
rewritten. What a type cannot say is that each behaviour still fires on the right SIDE, and
that is what `tests/mode-partition.test.ts` keeps: eight named per-behaviour rows plus the
headless metric split (`golden-widths` vs real per-em).

⚠️ **AND THE OBVIOUS CONTROL THERE IS WORTHLESS** — `strict(feature) !== extended(feature)`.
The two already differ on a bare `CDEF|`, so every row reads red and means nothing; a first
cut had three rows whose two digests were the PLAIN tune's. Rows are paired WITHIN one mode.

✅ `ABCJS-DIFFERENCES.md` has the two owed entries — the clef's declared zero edge and the
held syllable's line height — and its `<defs>`/`<use>` claim is corrected from 0.33x to
**0.446x**, measured over all 691 against abcjs's own bytes.
