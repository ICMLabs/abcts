### 1. `S3-note-syntax-tune13` — 0.26px of staff line

The staff-line gate's one remaining target. 0.26px of CENTRE, so 0.52 of span, on X:314
"Rests" — a tune that is nothing but rests, justified. Our right end is half a pixel short
of abcjs's `staffGroup.w`. Every notehead on it is exact, so it is the justification TARGET
at the right edge and not a placement. Cheap, and it empties the third gate.

### 2. THE ABOVE-LANE ORDER — the last structural item in geometry

abcjs spends every above lane in ONE loop, in order — chord, ending, dynamic, part, tempo
(`set-upper-and-lower-elements.js:31-49`). We spend them in FOUR places:

```
anchorAboveStaff       chord, part, tempo
verticalExtent         the ENDING lane, the DYNAMIC lane
anchorDynamicsAbove    the dynamic MARK          (finding 146)
```

The staff's TOTAL is right either way — both corpora prove it — so **no gate can see this**.
What differs is which lane a mark lands in when a staff carries TWO: a tempo mark over a
volta draws inside the ending lane; an above dynamic on a staff with a chord lane lands in
the chord's space.

**BUILD THE LADDER FIRST — nothing in either corpus combines them.** Two controls settle it:
a staff with a chord symbol AND an above dynamic, and one with a volta AND a tempo mark.
Instrument abcjs's `staff.top` and its `positionY` map on both; the probe point is already
written down and has earned its keep eight times.

Three `ponytail:` notes defer to this — the ending bracket's (93), the tempo mark's, and the
above dynamic's (146). It is the most regression-prone code in the file, and both ranked
tables at 0 is the best safety net it will ever have.

### 3. AUDIO — and the FIRST COMMIT IS THE HARVESTER

Do not start by porting `abc_midi_flattener.js`. There is no audio gate at all, and this
repo's own history says what that costs: every gate it has was worth more than the fix it
enabled, and finding 144 is the newest proof.

**The inputs are already here.** 61 of the 174 harvested fixtures are abcjs's synth tests,
paired in `SOURCES.json`:

```
46  tests/synth/flattener.test.js
12  tests/synth/timing.test.js
 3  tests/synth/midi.test.js
```

**The expected output is already written down.** `flattener.test.js` is 8,203 lines, almost
all of it expected event lists as JSON literals:

```js
{ "cmd": "note", "pitch": 67, "volume": 85, "start": 0,
  "duration": 0.125, "instrument": 0, "gap": 0 }
```

wrapped in `{tempo, instrument, tracks[]}`. `timing.test.js` adds 526 more. That is an EXACT
oracle of the same kind as the `.parse.json` and `.elements.json` goldens.

So the arc is:

1. **`npm run harvest:audio`** — extract the `expected*` objects from those three files and
   pair them to the fixtures already on disk. `harvest-abcjs-tests.mjs` is the model for
   the extraction; `harvest-abcjs-goldens.mjs` currently shells out to `dump-svg.js` and
   captures SVG only.
2. **A ranked table**, the third of its kind — per fixture, the first event that differs.
   It will start at 61 of 61 and that is the point.
3. **`%%MIDI` in the parser.** Zero occurrences today. `program`, `bassprog`, `chordprog`,
   `gchord`, `drum`, `percmap`, `channel`, `transpose`.
4. **The flattener**, against the table. `abc_midi_flattener.js` (31KB) is what the oracle
   tests; `abc_midi_sequencer.js` (26KB) and `chord-track.js` (22KB) are the rest of the
   parity surface.

**WHAT IS NOT PARITY WORK:** `create-synth.js`, `synth-controller.js`, soundfont loading,
WebAudio — ~90KB of host playback. A `{cmd, pitch, start, duration}` list compared against
abcjs's own is the whole gate; whether a host plays it through WebAudio, CoreAudio or a MIDI
file is that host's business. Same split the renderer already makes between geometry (in
scope) and glyph outlines (out).
